# Central Channel

Hotel and parking reservation management UI, customer booking handoff, and a Python REST service backed by Supabase PostgreSQL.

## Run locally

Install the PostgreSQL driver and configure your Supabase project first:

```powershell
python -m pip install -r "CENTRAL CHANNEL/requirements.txt"
```

Copy `CENTRAL CHANNEL/.env.example` to `CENTRAL CHANNEL/.env` and set `SUPABASE_DATABASE_URL` to the database connection string from your Supabase project's **Connect** dialog. Set `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from the project's API settings. Keep all keys in the local `.env`; `SUPABASE_SECRET_KEY` is server-only and is only required to run integration tests that create and remove test Auth users. The service creates its tables and seeds the initial room and parking inventory when it starts.

From the workspace root, start the service:

```powershell
python "CENTRAL CHANNEL/run.py"
```

Open `http://127.0.0.1:8000/` to see the NEXORA landing page before signing in. Supabase Auth manages passwords, optional confirmation emails, and bearer tokens. With email confirmation enabled, users can confirm by clicking the email link or entering the emailed code, then sign in; with confirmation disabled, signup signs them in immediately. When first-admin bootstrap is enabled, the first immediately signed-in or email-confirmed signup becomes the administrator; later signups receive the `User` role. The administrator can promote registered users to Hotel Personnel or Parking Personnel from the dashboard. To disable first-signup bootstrap, set `CENTRAL_FIRST_SIGNUP_ADMIN=0` and create the administrator interactively with:

```powershell
python "CENTRAL CHANNEL/run.py" --create-admin
```

When email confirmation is enabled, users can confirm by clicking the link or entering the fallback code. Open Supabase **Authentication → URL Configuration** and set **Site URL** to the public HTTPS address of the deployed NEXORA website; add any other deployed website addresses under **Redirect URLs**. Do not use `localhost` or `127.0.0.1` for links users must open from Gmail. Then open **Authentication → Email Templates → Confirm signup**, set the subject to `Confirm your NEXORA email address`, and replace the template body with the contents of [`supabase-confirm-signup-email.html`](./supabase-confirm-signup-email.html). Save the template. Its `{{ .ConfirmationURL }}` link is generated by Supabase, and the fallback `{{ .Token }}` remains usable on the signup screen. These Supabase dashboard settings must be saved in your project; changing this local repository alone cannot alter emails already sent or templates in Supabase. To send confirmation messages from Nexora Hotel, configure **Authentication → SMTP Settings** with sender `nexorahotel@gmail.com`, SMTP host `smtp.gmail.com`, port `465` (SSL) or `587` (STARTTLS), the Gmail username, and a Google app password. Keep the app password only in Supabase's SMTP settings; never put it in this repository or the browser.

Administrators can open the dedicated portal at `http://127.0.0.1:8000/admin`. Sign in with an account whose role is `Admin`; regular customer accounts are not granted admin access.

Admins can pause or resume reservation API access from the switch in the upper-right corner of the dashboard. While paused, non-admin reservation API requests are rejected; login and the Admin dashboard remain available so an Admin can resume service. The setting is stored in PostgreSQL, so it remains consistent across app replicas and backend restarts.

An existing administrator can create additional Admin accounts from **Personnel management → Create administrator account**. Enter a unique username and email and a password of at least 10 characters. Supabase email confirmation settings apply to newly created accounts; if confirmation is enabled, the new administrator must confirm their email before signing in. The form is available only to Admin users, and account creation uses the server's Supabase publishable key, not a service-role key.

On Windows, double-click `RUN_RESERVATION_SITE.bat` in the workspace root to start the backend if needed, wait for the database-backed readiness check, and open the landing page. The launcher reuses a healthy API already running on port 8000 instead of starting a duplicate. Keep the backend console window open while using the site; press Ctrl+C in that window to stop it. Run the launcher again to start the API after it has been stopped or the computer restarted. This is opt-in, launch-time startup; it does not install a Windows startup task or keep the API available when this computer is off.

`SUPABASE_DATABASE_SCHEMA` selects the PostgreSQL schema (default `public`). `CENTRAL_HOTEL_EMAIL` sets the hotel's contact email (default `nexorahotel@gmail.com`). The other `.env` settings configure the host, port, session lifetime, first-admin bootstrap, allowed origins, or an external API base URL.

## Production traffic and operations

The API keeps Supabase bearer-token authentication and server-side role/ownership checks for every protected endpoint. It applies a general API limit (default 120 requests per minute per client IP), with tighter limits for login (10/minute), registration and email-code verification (5/hour), confirmation-code resend (10/hour), token refresh (30/minute), and customer problem reports (5/hour). A 429 response includes `Retry-After`. Configure the limits with the `CENTRAL_*_RATE_LIMIT_*` settings in `.env.example`. Supabase may also apply its own email-send limits independently of this app-side limit.

Set `CENTRAL_REDIS_URL` to a private Redis/Valkey service in production. This makes rate limits atomic and shared across replicas; if Redis is configured but unavailable, requests fail with 503 rather than bypassing the protection. Without it, the development fallback is process-local, is reported as `rateLimitMode: "local"` by the readiness endpoint, and is not suitable for a load-balanced deployment. When behind a reverse proxy or load balancer, set `CENTRAL_TRUSTED_PROXY_CIDRS` to only the proxy CIDRs so client IPs can be read safely from forwarded headers. Do not trust arbitrary forwarded headers.

`GET /api/health/live` is a liveness check independent of database connectivity. `GET /api/health/ready` (also available at the existing `/api/health`) checks PostgreSQL and a configured Redis service. API responses carry an `X-Request-ID`; JSON access/error logs include the request ID, status, path, and duration without logging request bodies or bearer tokens. Database initialization retries transient startup connection failures, and the threaded server waits for active requests during shutdown. For production, run behind HTTPS and a production-grade reverse proxy/load balancer, use multiple app replicas only with shared Redis, and enable managed database backups/point-in-time recovery and centralized log retention/alerting.

The customer Help panel provides a sanitized service-status check, recovery guidance, and a problem-report form. Reports are limited to 2,000 characters, rate-limited (default 5 per hour per client IP), stored in PostgreSQL, and visible only in the Admin dashboard's **Guest reports** section. When Gmail SMTP is configured, each report is also emailed to `CENTRAL_HOTEL_EMAIL`, and Admins can reply from the report panel; replies are emailed to the guest and saved in the report thread. Configure `CENTRAL_SMTP_USERNAME=nexorahotel@gmail.com`, `CENTRAL_SMTP_PASSWORD` with a Google App Password, and `CENTRAL_SMTP_SENDER=nexorahotel@gmail.com` in the server-side `CENTRAL CHANNEL/.env`, then restart the service. The account must have 2-Step Verification enabled to create a Google App Password; do not use the regular Gmail password. Without SMTP credentials, reports are still stored and shown in Admin, but email delivery and replies are unavailable and the page reports that clearly. A recent failed request ID is attached when available; reports do not include stack traces, credentials, or request bodies. Customer and Admin browser sessions use separate storage keys so one portal does not overwrite the other's session. After updating from a build that used the old shared session key, each account must sign in once again. Customer-facing tools do not expose internal logs or provide database recovery controls. Database backup and restore remain hosting-provider operations and must be configured and tested separately.

The development static-file host does not serve dotfiles, backend source, dependency manifests, or local database files. Keep production secrets in the hosting platform's secret manager rather than in deployed static assets.

## REST API

The service exposes bearer-token authentication at `/api/auth/register`, `/api/auth/login`, `/api/auth/me`, and `/api/auth/logout`. Customer support uses `GET /api/health/ready` for the service-status check and `POST /api/support/reports` to submit a report; `GET /api/admin/support/reports` is Admin-only. Booking endpoints include:

- `GET /api/admin/reservations/status`, `PUT /api/admin/reservations/status` (Admin-only reservation availability control)
- `GET /api/admin/audit-log` (Admin-only recent privileged actions)

- `GET /api/bookings`, `GET /api/hotel/bookings`, `GET /api/parking/bookings`
- `POST /api/hotel/bookings`, `POST /api/parking/bookings`
- `POST /api/combined/bookings` (creates a hotel reservation and parking add-on together)
- `PUT /api/bookings/{id}/accept|approve|reject|cancel|check-in|check-out|assign`
- `PATCH /api/bookings/{id}`
- `GET /api/rooms`, `GET /api/parking/slots`
- `GET /api/personnel`, `GET /api/notifications`, `GET /api/history`

`CENTRAL_API_BASE` may be set on `window` before `api-client.js` loads to target a compatible external REST service. The default uses the current web origin for hosted sites and the local backend at `http://127.0.0.1:8000` when opened as a file or served from a localhost port other than 8000.

The Admin Central request queue fetches the latest bookings every 5 seconds while visible, including automatically approved reservations, and has a manual refresh control. It displays the last successful sync time and preserves the last loaded queue if a refresh fails. Other Admin data refreshes on page load and when the page regains focus. Customer booking panels refresh while visible and on focus using 5-second polling. These are near-real-time HTTP refreshes, not Supabase Realtime/WebSocket subscriptions; they require no public table publication and reload authoritative state after missed refreshes. Admin capacity figures are loaded from current database inventory, not fixed room/space assumptions. The NEXORA hotel walkthrough reads room and parking availability from the API when it starts and refreshes every 5 seconds while visible. It evaluates availability for the current day/hour, maps database room numbers and parking slot codes to scene objects, and opens the reservations page for booking. The walkthrough is a live, read-only inventory view; selecting a 3D space does not reserve it.

## Roles and data

Roles are `Admin`, `Hotel Personnel`, `Parking Personnel`, and `User`. API authorization limits personnel to their department and users to their own reservations. Supabase Auth verifies passwords and bearer tokens; the app stores profile, role, and customer support report data in PostgreSQL and refreshes expiring access tokens. Booking creation, edits, approval, check-in/out, and resource assignment serialize against a shared database lock so overlapping assignments cannot race; invalid date windows and conflicting edits are rejected. Resource status is recalculated from remaining approved and checked-in bookings before a room or slot is released. Reservation lifecycle changes are written to `BookingHistory`; privileged Admin actions are recorded in `AuditLog`, available to Admins through `GET /api/admin/audit-log`.

Reservation checkout supports manual Cash or Bank transfer selection. Payment status is stored separately and remains `Pending`; there is no payment provider, charge, or captured transaction amount. The hotel checkout's parking add-on collects vehicle, plate, arrival/departure times, and an optional specific space. `POST /api/combined/bookings` accepts `name`, `email`, optional `phone` and `paymentMethod`, plus `hotel` (`property`, `roomType`, `checkIn`, `checkOut`, `guests`, optional `notes`) and `parking` (`property`, `vehicle`, `plate`, `parkingDate`, `parkingTime`, `parkingEndTime`, `durationHours`, optional `slotId` and `notes`) objects. The parking window must be within the hotel stay, and the API verifies its duration against the submitted departure time. Both bookings are linked by a `BookingGroups` ID and are created in one database transaction; if either room or parking space cannot be assigned, the API returns `409` and rolls back both records. On success the response contains the group `id`, serialized `hotel` and `parking` bookings, and `paymentStatus: "Pending"`. Combined bookings require both resources to be available and are automatically approved; they do not become separate pending bookings. Their QR pass pairs the exact hotel and parking records using the group ID. The add-on's displayed `$18` is an estimate, not a stored charge or payment. Standalone parking guests can select a specific available space from the live slot map before proceeding to checkout; the API rechecks and reserves that selected space during booking creation, rejecting the request if another booking claimed it meanwhile. Standalone bookings with available inventory are automatically approved and assigned in the same transaction. If standalone inventory is unavailable, an unassigned request remains Pending for Admin or matching personnel to review. The PostgreSQL schema includes Users, Personnel, BookingGroups, HotelBookings, Rooms, ParkingBookings, ParkingSlots, Vehicles, Notifications, BookingHistory, AuditLog, and Sessions. Existing records in the old SQLite file are not copied automatically; export/import them before switching if they need to be retained.

The browser uses the REST API and does not connect directly to PostgreSQL or Supabase table APIs. Authorization is enforced by the API; this project does not install PostgreSQL row-level-security policies. Do not expose database credentials to the browser. Keep the API database role restricted to the application schema and configure/test managed backups and point-in-time recovery with the database provider; backup restore and production error-monitoring services are not provisioned by this repository.

The included HTTP server is intended for local development; production deployments should use HTTPS, a production WSGI/ASGI server, and a restricted `CENTRAL_ALLOWED_ORIGINS` value.

The customer page can display sample prices in USD, EUR, GBP, or PHP. EUR, GBP, and PHP display values use Frankfurter's latest published USD exchange rates, refreshed when the page opens and periodically while it remains open. If the rate service is unavailable, the page uses the last saved rates and shows their publication date. These are indicative display conversions only: the reservation API does not charge a payment or store a converted transaction amount.

## Tests

```powershell
Push-Location "CENTRAL CHANNEL"
python -m pip install -r requirements.txt
python -m unittest backend.test_api -v
Pop-Location
```

API integration tests create and remove a uniquely named schema and temporary Supabase Auth users, so run them only against a development project. They are skipped unless the database URL, Supabase URL, publishable key, and server-only secret key are configured.
